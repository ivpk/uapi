1. Paskirtis

Dokumentas aprašo saugumo protokolą, kuriuo apsaugotos UDTS duomenų paslaugos: kaip duomenų gavėjo sistema autentifikuojasi, gauna prieigos žetoną ir su juo gauna duomenis, ir ką tikrina API vartai bei Spinta agentas.

Dokumentas skirtas:

  • duomenų gavėjų sistemų kūrėjams;
  • duomenų teikėjams, kurie pildo Duomenų perdavimo paslaugos užsakymą VIISP platformoje. Skiltyje „Saugumas“ pasirenkamas protokolas OAuth2, o dokumentacija pateikiama nuoroda į šį puslapį.

Visos Spinta agento teikiamos UDTS paslaugos autentifikuoja vienodai, todėl dokumentas bendras. Paslaugos skiriasi tik adresu ir leidimais (scope).

4. Prieigos suteikimas

Prieigą suteikia duomenų teikėjas, kai gavėjas turi pagrindą gauti duomenis (pvz., duomenų teikimo sutartį). Teikėjas:

  1. agente sukuria gavėjo klientą su sutartyje numatytais leidimais: rankiniu būdu arba automatizuotomis priemonėmis, automatiškai pagal išmaniąją sutartį;
  2. vartuose užregistruoja gavėjo aplikaciją (jos Client ID yra agento išduotas kliento identifikatorius) ir užprenumeruoja ją paslaugos API rakto ir OAuth2 planams;
  3. saugiai perduoda gavėjui kliento vardą, slaptažodį ir API raktą: saugiu kanalu arba užšifruotus gavėjo viešuoju raktu (tada juos iššifruoti gali tik gavėjas savo privačiuoju raktu).

Gavėjui reikalingi duomenys ir iš kur jie gaunami:

5. Užklausų srautas

A. Žetono gavimas

  1. Gavėjo sistema siunčia POST /:token vartams su dviem prieigos duomenimis, kuriuos gavo iš teikėjo (žr. 4 skyrių): API raktu vartams ir kliento vardu bei slaptažodžiu agentui (HTTP Basic).
  2. Vartai patikrina API raktą ir perduoda užklausą agentui (/auth/token).
  3. Agentas patikrina kliento vardą, slaptažodį ir prašomus leidimus, tada išduoda pasirašytą JWT žetoną.

B. Duomenų užklausa

  1. Gavėjo sistema siunčia duomenų užklausą su žetonu (Authorization: Bearer).
  2. Vartai patikrina žetoną agento introspekcijos taške (/auth/introspect) ir tai, ar žetono klientas turi galiojančią prenumeratą.
  3. Vartai perduoda užklausą agentui. Agentas dar kartą patikrina žetono parašą ir galiojimą, taip pat ar leidimai apima užklausiamus duomenis.
  4. Agentas gauna duomenis iš šaltinio ir grąžina atsakymą.

6. Žetono gavimas

POST {bazinis adresas}/:token
X-Gravitee-Api-Key: {API raktas}
Authorization: Basic {base64("kliento vardas:slaptažodis")}
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope={leidimai, atskirti tarpu}
ParametrasPrivalomasReikšmė
grant_typeTaipclient_credentials
scopeTaipPrašomi leidimai, atskirti tarpu. Galima prašyti tik tų leidimų, kurie suteikti klientui. Paprašius kito leidimo, žetonas neišduodamas.

Pavyzdys su curl:

SERVER=https://apigw.gov.lt/datasets/gov/vssa/demo/demo_udts/1
CLIENT=imone-sistema      # kliento vardas
SECRET=...                # kliento slaptažodis
API_KEY=...               # API raktas
SCOPES="uapi:/datasets/gov/vssa/demo/demo_udts/1/:getall uapi:/datasets/gov/vssa/demo/demo_udts/1/:getone"

TOKEN=$(curl -sS -f \
  -H "X-Gravitee-Api-Key: $API_KEY" \
  -u "$CLIENT:$SECRET" \
  -d "grant_type=client_credentials" \
  --data-urlencode "scope=$SCOPES" \
  "$SERVER/:token" | jq -r .access_token)

Atsakymas:

{
  "token_type": "Bearer",
  "access_token": "eyJ…",
  "expires_in": 864000,
  "scope": "uapi:/datasets/gov/vssa/demo/demo_udts/1/:getall uapi:/datasets/gov/vssa/demo/demo_udts/1/:getone"
}

Žetono turinys:

LaukasReikšmė
issAgento, kaip autorizacijos serverio, identifikatorius
sub, client_idKliento identifikatorius (UUID). Abu laukai sutampa, nes klientas veikia savo vardu.
audResursų serverio (agento) identifikatorius

Žetoną saugokite ir naudokite pakartotinai, kol jis galioja. Naujo prašykite tik baigiantis expires_in laikui arba gavę atsakymą 401. Neprašykite naujo žetono kiekvienai užklausai: vartuose taikomas užklausų dažnio ribojimas.

7. Duomenų užklausos

Duomenų užklausose siunčiamas tik žetonas:

curl -sS "$SERVER/rctest/Country" -H "Authorization: Bearer $TOKEN"

Techniniams keliams naudojamas tik API raktas:

curl -sS "$SERVER/:version" -H "X-Gravitee-Api-Key: $API_KEY"
curl -sS "$SERVER/:health"  -H "X-Gravitee-Api-Key: $API_KEY"

Užklausų sintaksė ir atsakymų formatas aprašyti UDTS specifikacijoje, konkrečios paslaugos keliai – jos OpenAPI apraše.

8. Leidimai (scope)

Leidimo formatas apibrėžtas UDTS specifikacijoje:

uapi:/{kelias}/:{veiksmas}
VeiksmasLeidžia
getoneGauti vieną įrašą pagal identifikatorių
getallGauti įrašų sąrašą
searchFiltruoti ir ieškoti įrašų
changesGauti pakeitimų istoriją

Leidimas galioja nurodytam keliui ir viskam, kas po juo:

LeidimasKam galioja
uapi:/datasets/gov/vssa/demo/demo_udts/1/:getallVisiems paslaugos modeliams
uapi:/datasets/gov/vssa/demo/demo_udts/1/rctest/:getallVisiems duomenų rinkinio rctest modeliams
uapi:/:getallVisiems šio agento teikiamiems duomenims

Konkrečius leidimus nurodo duomenų teikėjas, kai suteikia prieigą. Agentas kiekvieną užklausą tikrina: žetone turi būti bent vienas leidimas, apimantis užklausiamą modelį. Kitaip grąžinama klaida 403.

9. Ką tikrina vartai ir agentas

KurPriemonė
RyšysVisos užklausos tik per HTTPS. Vidiniai vartai pasiekiami tik iš SVDPT tinklo.
API vartai
  • API raktas techniniams keliams (/:token, /:version, /:health).
  • Duomenų keliams – žetonas, tikrinamas agento introspekcijos taške /auth/introspect. Introspekcijai vartai naudoja atskirą agento klientą, turintį tik leidimą uapi:/:auth_introspect.
  • Užklausa praleidžiama tik tada, kai žetono klientas turi galiojančią šios paslaugos prenumeratą.
  • Užklausų dažnio ribojimas pagal Duomenų perdavimo paslaugos užsakyme nurodytą apkrovą.
  • Užklausų atitikties paslaugos OpenAPI aprašui tikrinimas.
Spinta agentas
  • Žetono parašas (RS512, agento raktas), išdavėjas (iss), adresatas (aud) ir galiojimas (exp).
  • Leidimai kiekvienam užklausiamam modeliui ir savybei.
  • Kliento slaptažodis saugomas tik kaip maiša (PBKDF2-SHA256).
  • Prieigos žurnale registruojamas kliento identifikatorius ir žetono leidimai.

10. Prieigos atšaukimas ir duomenų apsauga

Atšaukimas

  • Teikėjas uždaro gavėjo prenumeratą vartuose. Nuo tada vartai to kliento užklausų nebepraleidžia.
  • Teikėjas pašalina klientą agente. Nuo tada nauji žetonai nebeišduodami.
  • Jau išduotas žetonas formaliai galioja iki exp, nes atšauktų žetonų sąrašo nėra. Todėl prieigą iš karto nutraukia prenumeratos uždarymas vartuose.
  • API raktą teikėjas gali pakeisti vartuose.

Gavėjo pareigos

  • Kliento slaptažodį ir API raktą saugokite kaip slaptažodžius: slaptažodžių saugykloje, ne programos kode ir ne kodo repozitorijoje.
  • Prieigos duomenis naudokite tik serverio pusėje, ne naršyklėje ar mobiliojoje programėlėje.
  • Nerašykite žetonų, slaptažodžių ir API raktų į žurnalus.
  • Kiekvienai sistemai ir aplinkai naudokite atskirus prieigos duomenis.
  • Įtarę, kad prieigos duomenys atskleisti, nedelsdami praneškite duomenų teikėjui.

12. Ryšys su UDTS specifikacija

Šis dokumentas aprašo, kaip šiuo metu įgyvendintas UDTS specifikacijos v1.1 skyrius „Authorization“. Įgyvendinta: Client Credentials srautas, JWT žetonai, UDTS leidimų formatas, žetono tikrinimas vartuose ir agente.

Kol kas kitaip, nei numatyta specifikacijoje:

  • žetoną išduoda pats paslaugos agentas, ne bendras autorizacijos serveris;
  • žetonas gaunamas per vartų kelią /:token;
  • vartai žetoną tikrina introspekcija agente, ne autorizacijos serverio viešuoju raktu;
  • klientai agente kol kas kuriami rankiniu būdu, automatinis jų kūrimas pagal išmaniąją sutartį dar neįgyvendintas;
  • srautas, kai sistema veikia konkretaus naudotojo vardu (Authorization Code), neįgyvendintas.

Kai įgyvendinimas keisis, šis dokumentas bus atnaujintas tuo pačiu adresu, o pakeitimai įrašyti į pakeitimų istoriją.
